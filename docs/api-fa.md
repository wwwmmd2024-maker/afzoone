# قرارداد سرور لایسنس و اتصال به فروشگاه

## واقعیت اتصال بازار

این پروژه **آداپتور رسمی ژاکت یا راست‌چین ندارد** و نمی‌تواند خریدی را که آن بازار به آن اطلاع نمی‌دهد شناسایی کند. انتخاب نام فروشگاه در پنل فقط برای دسته‌بندی سفارش است، نه اتصال به حساب شما در آن فروشگاه.

برای اتوماسیون واقعی:

۱. از بازار درباره وب‌هوک پرداخت، API تأیید سفارش، روش تحویل کد و اجازه استفاده از سرور لایسنس خارجی استعلام بگیرید.
۲. یک آداپتور مطابق اسناد همان بازار بنویسید که اصالت پیام، وضعیت پرداخت، محصول و مالکیت فروشنده را بررسی کند؛ در صورت لزوم وضعیت خرید را از API رسمی دوباره تأیید کند.
۳. **فقط پس از تأیید واقعی پرداخت** آداپتور رویداد سفارشی زیر را به سرور ما بفرستد.
۴. پاسخ را در سابقه سفارش خود نگه دارد و کد را از راه مجاز بازار به همان خریدار تحویل دهد. این سرور خودکار ایمیل یا پیام بازار ارسال نمی‌کند.
۵. تکرار درخواست باید همان `platform + order_id` را داشته باشد. این جفت، کلید یکتای سفارش است. در لغو/استرداد، آداپتور باید طبق سیاست شما API لغو را فراخوانی کند.

اگر بازار API یا تحویل سفارشی ندارد، راه آماده و قابل استفاده همین **صدور دستی در پنل** است. نباید وب‌هوک اختصاصی این پروژه را بدون آداپتور و بدون بررسی قرارداد، مستقیم به وب‌هوک یک بازار وصل کرد.

## درخواست‌های مدیریت

نشانی نمونه: `https://licenses.example.com/server.php?action=issue`

تمام عملیات API فقط `POST` با JSON هستند. هدر مدیریت:

```text
Authorization: Bearer YOUR_ADMIN_TOKEN
Content-Type: application/json
```

| action | بدنه | عملکرد |
|---|---|---|
| `init` | `{}` | ساخت کلید در اولین اجرا و دریافت کلید عمومی |
| `issue` | `{"platform":"manual","order_id":"123","expires_at":0}` | صدور یا بازیابی کد همان سفارش |
| `list` | `{"offset":0}` | حداکثر ۱۰۰ رکورد از جدید به قدیم؛ کدها ماسک‌شده |
| `revoke` | `{"license":"PIF-..."}` | لغو غیرقابل فعال‌سازی توسط مشتری |
| `reset` | `{"license":"PIF-..."}` | پاک‌کردن اتصال دامنه؛ لایسنس لغوشده را فعال نمی‌کند |

`expires_at` عدد صحیح Unix timestamp برحسب UTC است. صفر یعنی بدون انقضای رکورد. ورودی تاریخی در گذشته برای صدور رد می‌شود. تکرار سفارش، تاریخ انقضا یا وضعیت آن را تغییر نمی‌دهد. لایسنس لغوشده با صدور دوباره همان سفارش دوباره فعال نمی‌شود.

پاسخ صدور:

```json
{"ok":true,"license":"PIF-XXXXXXXX-XXXXXXXX-XXXXXXXX-XXXXXXXX","status":"active","existing":false}
```

کدهای X نمونه‌اند و معتبر نیستند. هیچ رمز مدیریت یا وب‌هوکی را در افزونه مشتری قرار ندهید. نمونه مستقیم cURL فقط از دستگاه امن شما:

```bash
curl --fail-with-body 'https://licenses.example.com/server.php?action=issue' \
  -H "Authorization: Bearer $PIF_ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"platform":"manual","order_id":"ORDER-123","expires_at":0}'
```

## وب‌هوک سفارشی آداپتور

`POST ?action=webhook`

```json
{
  "event": "purchase.completed",
  "status": "paid",
  "product": "product-image-finder",
  "platform": "rtl",
  "order_id": "ORDER-123",
  "expires_at": 0
}
```

هدرها:

- `X-PIF-Timestamp`: زمان فعلی Unix timestamp به ثانیه.
- `X-PIF-Signature`: خروجی hex کوچک HMAC-SHA256 با رمز خصوصی وب‌هوک روی `timestamp + "." + raw_request_body`.
- `Content-Type: application/json`.

اختلاف زمانی مجاز ۳۰۰ ثانیه است. امضا باید روی بایت‌های دقیق JSON ارسال‌شده ساخته شود. ساعت هاست‌ها را هماهنگ کنید. بازپخش در پنجره مجاز، برای همان سفارش کد جدید ایجاد نمی‌کند. این امضا **بین آداپتور شما و سرور شما** است؛ امضای واقعی بازار باید جداگانه توسط آداپتور تأیید شود.

نمونه مرجع در `tools/send_webhook.py`:

```bash
# PIF_WEBHOOK_SECRET را به‌صورت امن در محیط همین پردازش تنظیم کنید.
# این فرمان خودش خرید بازار را بررسی نمی‌کند!
python3 tools/send_webhook.py \
  --url https://licenses.example.com/server.php \
  --platform rtl --order-id ORDER-123
```

## درخواست افزونه مشتری

`POST ?action=activate` یا `POST ?action=verify`، بدون رمز مدیریت:

```json
{"license":"PIF-...","domain":"shop.example.com","product":"product-image-finder"}
```

اولین اتصال دامنه فقط در `activate` انجام می‌شود. پاسخ موفق:

```json
{"ok":true,"token":"BASE64URL_PAYLOAD.BASE64URL_SIGNATURE"}
```

پروتکل امضا، یک **توکن سفارشی دو‌بخشی** است، نه JWT. امضا RSA PKCS#1 v1.5 با SHA-256 روی متن BASE64URL بخش اول است. ادعاها شامل نسخه، محصول، دامنه، SHA-256 لایسنس، `iat` و `exp` هستند. عمر حداکثر ۸۶۴۰۰ ثانیه است و از تاریخ انقضای لایسنس جلو نمی‌رود. افزونه امضا را با کلید عمومی ثابت داخل بسته تأیید می‌کند؛ کلید عمومی را در زمان اجرا از پاسخ شبکه قبول نمی‌کند.

## خطاها و ظرفیت

پاسخ خطا: `{"ok":false,"error":"error_code"}`.

- `401`: رمز مدیریت یا امضای وب‌هوک نادرست.
- `403`: لایسنس نامعتبر/لغوشده/منقضی، دامنه یا محصول ناسازگار، یا نیاز به فعال‌سازی.
- `400`: ورودی نامعتبر یا رویداد پشتیبانی‌نشده.
- `405`: متد نامعتبر.
- `413`: بدنه بیشتر از ۱۶ کیلوبایت.
- `426`: HTTPS لازم است.
- `429`: سقف ۶۰ درخواست فعال‌سازی/بررسی در دقیقه برای IP اتصال مستقیم.
- `503`: پیکربندی، پوشه خصوصی یا راه‌اندازی ناقص.
- `500`: خطای داخلی یا خرابی فایل؛ فایل خراب عمداً با پایگاه خالی جایگزین نمی‌شود.

سرور پشت پراکسی به `X-Forwarded-For` اعتماد نمی‌کند؛ محدودیت IP ممکن است برای همه درخواست‌های پراکسی مشترک شود. تنظیم IP واقعی باید در وب‌سرور و با اعتماد محدود انجام شود. محدودسازی مدیریت و وب‌هوک را علاوه بر احراز هویت، با فایروال وب‌سرور تقویت کنید.

فایل txt در هر درخواست خوانده می‌شود؛ این طراحی برای فروش کم تا متوسط روی یک هاست است، نه هزاران درخواست همزمان. برای مقیاس بالا، صف و پایگاه داده تراکنشی و کنترل ظرفیت جدا لازم است.
